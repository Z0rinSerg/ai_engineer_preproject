# Кто такой ИИ-инженер и что вас ждёт

## ИИ-инженер (AI Engineer)

```
Это специалист, который проектирует системы на основе готовых языковых моделей:
собирает вокруг них инфраструктуру, пайплайны работы с данными, интеграции и инструменты оценки качества. 
```
Что это означает на деле:

* Пайплайны работы с LLM: поиск релевантной информации, управление контекстом, промптинг, постобработка ответов.
* Интеграция моделей с внешними источниками (документами, базами знаний, API).
* Настройка инференса и итеративное улучшение качества ответов.
* Выбор стека: облачный провайдер или локальное развёртывание, тип эмбеддингов, векторная база.

С готовыми ML- и DL-моделями работают несколько профессий — от классических разработчиков до дата-сайентиста, ML-инженера и ИИ-инженера, — но делают это по-разному. Основной инструмент ИИ-инженера — уже обученная LLM.

# Что такое RAG и как устроен ИИ-ассистент

В предыдущем уроке вы познакомились с ролью ИИ-инженера и настроили локальное рабочее место. Теперь всё готово для того, чтобы начать разбираться с архитектурой!

В этом уроке разберёмся, почему «просто LLM» не справляется и что именно ломается, как устроена RAG-система и из каких компонентов состоит, как выглядит пайплайн от вопроса пользователя до ответа. Заодно зафиксируем целевой вид функции-ассистента и подготовим окружение: установим Ollama, скачаем модель и датасет.

Казалось бы, всё просто: берём мощную языковую модель и задаём ей вопрос.

Разработчик спрашивает у «чистой» LLM: «Какой HTTP-метод использует эндпоинт `/api/generate` в Ollama и какие параметры обязательны?»
Модель отвечает убедительно — и, скорее всего, не совсем верно: имена полей могут быть выдуманными, обязательность параметров перепутанной, а возможностей, появившихся после даты обучения, не быть вовсе.
Когда LLM выдаёт уверенный, но неверный ответ — это галлюцинация. Для продуктовой системы это проблема: ассистент не должен выдумывать сигнатуры API, формат `modelfile.mdx` или шаги `troubleshooting.mdx`.

Проблему можно решить двумя способами:

1. Дообучить модель на документации Ollama (это дорого, долго и требует повторного обучения при каждом обновлении документации).
2. Давать модели нужную информацию в виде контекста прямо в запросе. Тогда она не будет «вспоминать», а ответит, опираясь на приложенные документы.

Второй путь называется RAG. Его и будем собирать.

``` 
RAG (Retrieval-Augmented Generation) — подход, при котором LLM отвечает не «из памяти», а на основе документов, найденных системой под конкретный запрос пользователя.
```
Расшифруем: Retrieval — поиск, Augmented — обогащение, Generation — генерация. Итого: генерация, обогащённая поиском.

RAG-система обычно выглядит как цепочка из нескольких шагов: сначала мы заранее готовим базу знаний, а потом используем её для ответа на вопрос пользователя. Сначала посмотрим на общую схему целиком, а уже затем разберём, из каких компонентов она состоит.

# Компоненты RAG-системы

RAG-система состоит из четырёх базовых частей: чанкинга, эмбеддингов, векторного поиска и промптинга с инференсом LLM. Это именно строительные блоки системы — то, из чего она собрана.
Отдельно от компонентов стоит пайплайн — порядок, в котором эти части работают при загрузке документов и ответе на запрос.
## 1. Чанкинг

Документы обычно длинные: в документации Ollama файл `api.md` — это десятки страниц, `modelfile.md` — ещё столько же. Подавать их в модель целиком нельзя по двум причинам.

Во-первых, у LLM ограничен размер контекстного окна — количество токенов, которое модель может обработать за один раз. Во-вторых, даже если документ помещается, поиск по нему целиком менее точен, чем по небольшим фрагментам: нужное легко теряется в длинном тексте.

Поэтому документы разбивают на чанки — смысловые фрагменты по 200–500 слов. Хорошо подобранный чанк содержит одну законченную мысль: описание одного эндпоинта, правило одного параметра Modelfile, ответ на один FAQ.
Результат этого этапа — список чанков, который хранится в файле или в базе и ждёт, когда его будут искать.

## 2. Эмбеддинги
Когда пользователь задаёт вопрос, системе нужно найти в базе чанков самые релевантные. Но как это происходит?
Поиск по ключевым словам ненадёжен. Пользователь спрашивает: «Как отправить запрос к модели?», а в документе написано: "To send a prompt, POST to /api/generate". Общих ключевых слов почти нет, а ответ — вот он.
Выручает семантический поиск — не по словам, а по смыслу. Для этого каждый чанк и каждый запрос переводятся в числовой вектор — эмбеддинг. 
```
Эмбеддинг — числовое представление текста в виде вектора фиксированной длины (например, 384 или 768 чисел). Эти векторы устроены так, что тексты с близким смыслом оказываются рядом в пространстве.
Допустим, модель эмбеддингов видит слова «запрос» и «prompt». У них нет совпадения по буквам, но в контексте документации они часто используются рядом с одной и той же задачей. Поэтому после преобразования в векторы они оказываются близко друг к другу. Так система понимает смысл, а не просто сравнивает совпадения слов.
```
## 3. Векторный поиск
Когда эмбеддинги всех чанков посчитаны и сохранены в векторном индексе, поиск становится простой операцией: считаем эмбеддинг запроса и ищем top-k чанков с самыми близкими векторами. Обычно k — это 3–5.
Результат этого этапа — несколько фрагментов документов, которые с высокой вероятностью содержат ответ на вопрос пользователя.
## 4. Промптинг и инференс LLM
Найденные чанки — это контекст. Его добавляют к пользовательскому вопросу и оформляют в виде промпта (инструкции для модели):
```
Ты ассистент по документации Ollama. Ответь на вопрос пользователя,
опираясь только на приведённые ниже фрагменты документации.
Если ответа в фрагментах нет, так и скажи.

Фрагменты документации:
<сюда вставляются top-k чанков>

Вопрос пользователя: <сюда вставляется запрос> 
```
Модель получает этот промпт и генерирует ответ, уже подкреплённый документацией. Шаг, когда LLM обрабатывает готовый промпт и возвращает ответ, **называется инференсом модели**.

Работа RAG-системы делится на два этапа:
## Этап 1. Индексация (выполняется один раз, заранее)

До первого вопроса пользователя мы готовим базу знаний:
1. Загружаем документы (PDF, TXT, Markdown).
2. Разбиваем их на чанки.
3. Считаем эмбеддинг для каждого чанка.
4. Сохраняем чанки и их эмбеддинги в индексе.

Это медленный и тяжёлый этап: каждый чанк нужно прогнать через модель эмбеддингов. Но и выполняется он один раз — при первоначальной загрузке документов или их обновлении.
## Этап 2. Ответ на запрос (каждый раз, когда пользователь спрашивает)
Это уже рантайм-часть (от англ. runtime — период, в который выполняется программа), и она должна работать быстро:
1. Считаем эмбеддинг запроса пользователя.
2. Ищем в индексе top-k ближайших чанков.
3. Собираем промпт из запроса и найденных чанков.
4. Отправляем промпт в LLM и получаем ответ.
5. Возвращаем ответ пользователю.

Такое разделение —  осознанное проектное решение. Основная тяжесть системы (эмбеддинги всех документов) посчитана заранее и лежит в индексе. Ответ получается быстрым, потому что на этапе запроса мы считаем всего один новый эмбеддинг (для самого вопроса) и делаем один поиск.

Прежде чем переходить к коду, зафиксируем конечную цель. Весь ваш ассистент к концу бесплатной части будет выглядеть как одна функция:
```python
def ask_assistant(question: str) -> str:
    # 1. Считаем эмбеддинг запроса
    query_embedding = embed(question)
    
    # 2. Ищем top-k релевантных чанков в индексе
    relevant_chunks = vector_search(query_embedding, top_k=3)
    
    # 3. Собираем промпт из запроса и найденных чанков
    prompt = build_prompt(question, relevant_chunks)
    
    # 4. Отправляем промпт в LLM и получаем ответ
    answer = generate_answer(prompt)
    
    return answer 
 ```   
Каждый компонент этого пайплайна мы будем собирать отдельно:
- функция `chunk_text` (и весь этап индексации) — в Уроке 3;
- функции `embed` и `vector_search` — в Уроке 4;
- функция `generate_answer` (вызов LLM через Ollama) — в Уроке 5;
- финальная сборка `ask_assistant` — в Уроке 6.
```
Такой подход — сначала зафиксировать интерфейс финальной функции, а потом собирать компоненты — типичная инженерная привычка. Вы заранее видите, как части стыкуются между собой, и не тратите время на реализацию того, что потом не встанет на место.
```
Пора подготовить LLM и данные для следующих уроков!
Сейчас вы сделаете два технических шага:
1. Установите Ollama и скачаете через него языковую модель.
2. Скачаете датасет документации Ollama.
## Что такое Ollama и зачем он нужен?

Ollama — это локальный сервер моделей. Вы устанавливаете его на компьютер один раз, и любой вызов LLM превращается в HTTP-запрос на `localhost`. Никаких API-ключей, никаких облаков — все данные остаются у вас.

После установки Ollama поднимает локальный сервер и принимает запросы. Именно так в Уроке 5 мы будем отправлять вопросы модели из Python — через обычные HTTP-запросы.

### Зачем нужно разбивать текст

В прошлом уроке мы коротко обозначили, зачем разбивать текст на чанки. Теперь разберёмся, почему это не техническая формальность, а решение, от которого напрямую зависит качество ответов ассистента. 
Но сначала — попробуйте вспомнить, что вы уже знаете.

## Три проблемы
У документа в `docs/` есть три проблемы с точки зрения LLM-системы.
## 1. Размер
У любой LLM ограничен размер контекстного окна — количество токенов, которое модель может обработать за один запрос. У Qwen 2.5 это 128 тысяч токенов, у некоторых моделей — всего 8 тысяч. Если положить в промпт весь файл `api.md`, плюс системную инструкцию, плюс вопрос и место под ответ — можно быстро упереться в ограничение.
## 2. Стоимость и скорость
Чем длиннее промпт, тем медленнее работает модель и тем больше памяти потребляет. На облачных API длинные промпты ещё и ощутимо дороже.
## 3. Качество поиска
Если документ длинный и затрагивает разные темы, его эмбеддинг получается «усреднённым»: одним вектором пытаемся описать и описание API, и инструкции по установке, и FAQ. Поиск по такому усреднённому представлению работает плохо — нужный фрагмент теряется внутри документа.
Решение всех трёх проблем — разбить документы на короткие смысловые фрагменты, чанки. Тогда:
- в LLM попадает только то, что относится к вопросу, и ничего лишнего;
- эмбеддинг каждого чанка точно описывает один кусочек смысла, и поиск становится прицельным;
- система работает быстрее и стабильнее.

```Чанк — короткий смысловой фрагмент документа. Хороший чанк содержит одну законченную мысль: описание одного эндпоинта, ответ на один вопрос FAQ, описание одного параметра.```

## Каким должен быть хороший чанкинг

Допустим, вы решили, что чанки нужны. Возникает следующий вопрос — как именно резать?

Самый прямолинейный подход — порезать текст на куски фиксированной длины (например, по 500 символов). Это работает, но плохо: разрез проходит посреди предложения или списка, а иногда даже посреди слова. Эмбеддинг такого обрубка получится мутным, потому что в нём перемешаны куски разных мыслей.
Другой подход — резать по структурным границам. В документации это естественно: каждый заголовок открывает новую тему, каждый параграф — новую мысль. Если резать по заголовкам, получается совсем другая картина: один чанк равен одной логически завершённой секции документа. Эмбеддинг такого чанка получается чётким и сфокусированным.
Однако здесь есть нюанс. Иногда секция получается слишком длинной — например, описание сложного эндпоинта со всеми параметрами и примерами может занимать десятки абзацев. Класть такое целиком в один чанк не хочется: эмбеддинг снова станет размытым, и в LLM будет уходить лишний текст. Поэтому длинные секции дополнительно дробят на куски поменьше — по параграфам.
Получается двухуровневый подход: сначала режем документ по структурным границам — заголовкам, затем слишком длинные секции дробим по параграфам. 
## Что значит «правильный размер»?
Жёсткого ответа не существует — всё зависит от данных и от того, какие вопросы задают пользователи. Размер чанка — это всегда компромисс, и у него есть два края.
Слишком короткие чанки — по 50–100 символов. Поместится ли туда хотя бы одна законченная мысль? Сможет ли LLM ответить по такому обрывку?
Слишком длинные — по 3000+ символов. Вспомните проблему «усреднённого эмбеддинга»: если в один чанк попадёт сразу несколько разных тем, поиск снова станет неточным.
Где-то между этими крайностями лежит рабочий диапазон. В уроке возьмём за стартовое значение 800 символов — но не потому что это магическое число. В практическом задании вы сами запустите функцию с разными значениями, посмотрите на результат и проверите, разумный ли это выбор для нашей документации.

## Готовая функция чанкинга

Чтобы не тратить время на реализацию с нуля, мы дадим вам готовую функцию chunk_text(). Её задача — принять текст и вернуть список чанков по описанной выше логике: режем по заголовкам уровня ##, длинные секции дробим по параграфам, слишком короткие куски (одни заголовки без содержания) выкидываем.

```python
def chunk_text(text: str, max_chars: int = 800, min_chars: int = 50) -> list[str]:
    """Режет Markdown по заголовкам ##; длинные секции дробит по параграфам.
    Параметры:
        text: исходный Markdown-текст
        max_chars: максимальная длина одного чанка в символах
        min_chars: минимальная длина чанка - чанки короче выбрасываются
    Возвращает:
        Список текстовых чанков
    """
    lines = text.split("\n")
    sections, current = [], []
    for line in lines:
        if line.startswith("## ") and current:
            sections.append("\n".join(current).strip())
            current = [line]
        else:
            current.append(line)
    if current:
        sections.append("\n".join(current).strip())

    chunks = []
    for section in sections:
        if not section:
            continue
        if len(section) <= max_chars:
            chunks.append(section)
            continue
        # Длинную секцию дробим по двойным переносам (параграфам)
        buf = ""
        for paragraph in section.split("\n\n"):
            if len(buf) + len(paragraph) + 2 <= max_chars:
                buf = f"{buf}\n\n{paragraph}" if buf else paragraph
            else:
                if buf:
                    chunks.append(buf.strip())
                buf = paragraph
        if buf:
            chunks.append(buf.strip())

    return [c for c in chunks if len(c) >= min_chars]
```
Пошагово разберём, что здесь происходит.
Первый цикл проходит по строкам файла и собирает их в секции. Когда встречается строка, начинающаяся с `##` (заголовок второго уровня), текущая секция закрывается и начинается новая. Так документ распадается на логические части.
Второй цикл проходит по секциям. Если секция короче `max\_chars` — она целиком становится чанком. Если длиннее — дробим её по двойным переносам строк (параграфам), складывая параграфы в буфер до тех пор, пока буфер не подойдёт к лимиту.
В конце выкидываем чанки короче `min_chars` — это, как правило, секции, состоящие из одного заголовка без содержания.
Параметры `max_chars=800` и `min_chars=50` подобраны эмпирически для технической документации. В практическом задании посмотрим, что произойдёт, если их менять.

## Загружаем документы и нарезаем

Прежде чем что-то нарезать, документы нужно прочитать. В `docs/` лежат файлы двух расширений — `.md` и `.mdx.` Содержимое у них одинаковое по структуре (Markdown), отличие только в том, что `.mdx` поддерживает JSX-вставки. Нам это неважно: читаем оба типа как обычный текст.

DOCS_DIR = Path("ollama_docs")

- При `max\_chars`=800 (наш дефолт) картина сбалансированная: каждый чанк содержит законченную мысль и не перегружен лишним текстом.
- При `max\_chars`=3000 чанки становятся крупными и могут содержать сразу несколько разных тем — та самая проблема размытого эмбеддинга, о которой говорили в начале урока.

Ключевой вывод: `max\_chars` — не магическое число, а параметр, который настраивают под характер данных. Для коротких справочных заметок лучше идут чанки поменьше, для длинных описаний — чуть побольше. На технической документации хорошо работают значения 600–1000 символов.

# Эмбеддинги и векторный поиск
В прошлом уроке вы разбили документы на чанки. Теперь у вас есть список из пары сотен коротких смысловых фрагментов — но как по нему искать?

В этом уроке вы познакомитесь с эмбеддингами — числовыми представлениями текста. Кроме того, разберётесь, что такое семантический поиск и почему он работает, превратите чанки в эмбеддинги, построите векторный индекс и получите первые результаты поиска по реальному запросу.
В конце урока ваш ассистент уже сможет находить релевантные фрагменты документации — останется подключить LLM, чем мы займёмся уже в следующем уроке.
## Эмбеддинги: текст как точка в пространстве
Идея, лежащая в основе семантического поиска, проста: каждый текст превращается в точку в многомерном пространстве так, чтобы тексты с близким смыслом оказывались рядом.
Эта точка — вектор фиксированной длины из чисел — и называется эмбеддингом (англ. embedding).

```
Эмбеддинг — числовое представление текста в виде вектора фиксированной длины (например, 384 или 768 чисел). Тексты с близким смыслом имеют близкие эмбеддинги, с далёким — далёкие.
```
## Откуда модель знает смысл?
Эмбеддинги — не продукт магии. Их выдают специально обученные модели — чаще всего на основе той же архитектуры Трансформер, что и LLM. Эти модели обучались на миллиардах пар текстов: «вот эти два предложения о похожем, эти два — о разном». В результате модель учится отображать тексты в векторное пространство, где близость векторов соответствует близости смыслов.

Хорошие новости: обучать такую модель самому не нужно. В открытом доступе есть десятки готовых моделей эмбеддингов. Мы возьмём одну из самых популярных компактных моделей — `paraphrase-multilingual-MiniLM-L12-v2`. Она многоязычная (включая русский), даёт векторы длиной 384 числа и весит около 470 МБ.
Модель эмбеддингов — такой же компонент стека ИИ-инженера, как и LLM. Только LLM генерирует текст, а модель эмбеддингов превращает его в вектор.
# Векторный поиск: ищем ближайших соседей
Допустим, вы посчитали эмбеддинги для всех 200 чанков из датасета. Получился список из 200 точек в 384-мерном пространстве. Когда пользователь задаёт вопрос, происходит следующее:
- Считается эмбеддинг вопроса.
- В облаке находятся 3–5 ближайших к нему точек.
- Соответствующие им чанки и становятся результатом поиска.
Этот подход называется поиском ближайших соседей (англ. nearest neighbours) или векторным поиском. Параметр `k` задаёт, сколько соседей мы хотим получить — обычно 3 или 5.
## Как измерять близость
Чтобы найти ближайшие точки, нужно уметь измерять расстояние между векторами. В семантическом поиске чаще всего используют косинусную близость: 
- значение около 1 — векторы смотрят почти в одну сторону, есть семантическая близость;
- около 0 — векторы перпендикулярны, тексты не связаны;
- отрицательные значения — тексты противоположны по смыслу (на практике встречается редко).
Расстояние можно измерять и по-другому (например, евклидовым расстоянием). Но для нормализованных эмбеддингов, которые выдаёт большинство современных моделей, обе метрики дают одинаковый порядок ближайших соседей. На результат поиска выбор практически не влияет.
## FAISS: быстрый поиск ближайших соседей
При 200 чанках можно сравнивать вектор запроса со всеми по очереди — это занимает миллисекунды. Но при 100 тысячах или миллионе чанков перебор становится дорогим. В продакшне для этого используют векторные индексы — специальные структуры данных, которые умеют быстро находить ближайших соседей.

Самая популярная опенсорс-библиотека — FAISS (Facebook AI Similarity Search), написанная на C++. Она ищет в миллионных коллекциях за миллисекунды. 
Для нашего объёма данных подойдёт простейший тип индекса — IndexFlatIP. Он сравнивает запрос со всеми векторами по очереди, без приближений — и для нескольких сотен чанков этого достаточно.
``Векторный индекс — структура данных, которая хранит эмбеддинги и позволяет быстро находить top-k ближайших к заданному вектору. Примеры: FAISS, Chroma, Qdrant.``

# Считаем эмбеддинги для чанков

Пора переходить к коду. Сейчас понадобятся две библиотеки — они уже должны быть в вашем виртуальном окружении из урока «Кто такой ИИ-инженер и что вас ждёт»:
```

``` 
Загрузим модель эмбеддингов и посчитаем векторы для всех чанков. Сами чанки — это переменная `chunks`, которую вы собрали ранее.

Параметр `normalize_embeddings=True` приводит каждый вектор к единичной длине. Это нужно, чтобы потом косинусная близость была эквивалентна обычному скалярному произведению — так будет удобнее работать с FAISS.

Параметр `show_progress_bar=True` нарисует прогресс-бар — на 200 чанках расчёт занимает 10–30 секунд на CPU.

В результате получаем матрицу chunk_embeddings размером (N, 384), где N — количество чанков, а каждая строка — эмбеддинг одного чанка.

# Строим векторный индекс
Теперь упакуем эмбеддинги в FAISS-индекс:
```python
import faiss

dim = chunk_embeddings.shape[1]  # 384
index = faiss.IndexFlatIP(dim)
index.add(chunk_embeddings)

print(f"В индексе {index.ntotal} векторов размерности {dim}")
```
Примерно такой вывод мы можем получить:
```

```
Здесь `IndexFlatIP` — это «плоский» индекс с метрикой Inner Product (скалярное произведение). Так как наши векторы нормализованы, скалярное произведение и есть косинусная близость.

Метод index.add() принимает матрицу (N, dim) и добавляет каждую строку как отдельный вектор. После вызова в индексе хранится N векторов, по которым можно искать.
# Первый поиск

Соберём всё в одну удобную функцию `vector_search()`:

```python
def vector_search(question: str, top_k: int = 3) -> list[dict]:
    """Возвращает top_k чанков, наиболее близких к запросу по смыслу."""
    # 1. Считаем эмбеддинг запроса
    query_emb = embed_model.encode(
        [question],
        normalize_embeddings=True,
    ).astype(np.float32)

    # 2. Ищем ближайших соседей
    scores, indices = index.search(query_emb, top_k)

    # 3. Собираем результат с метаданными
    results = []
    for score, idx in zip(scores[0], indices[0]):
        results.append({
            "text": chunks[idx]["text"],
            "source": chunks[idx]["source"],
            "score": float(score),
        })
    return results
```
    Здесь логика повторяет алгоритм поиска по облаку точек:
1. Превращаем запрос в вектор той же моделью, что и чанки.
2. Просим у индекса top-k ближайших.
3. Для каждого попадания возвращаем сам текст чанка, его источник и оценку близости.
Проверим:

```python

print(f"Запрос: {question}\n")
for i, r in enumerate(results, 1):
    print(f"#{i}  [{r['source']}]  score={r['score']:.3f}")
    print(r["text"][:200], "...\n")
```

## LLM как сервис: что такое инференс

Когда вы скачали модель Qwen 2.5 командой `ollama pull qwen2.5:1.5b`, её веса легли в локальное хранилище. Но сами по себе веса — это просто файл с числами; чтобы получать ответы, нужно запустить инференс.
```
Инференс — это процесс, в котором обученная модель принимает на вход текст и возвращает результат (в случае LLM это сгенерированный продолжающий текст). В отличие от обучения, веса при инференсе не меняются.
```
Ollama берёт эту работу на себя: при установке она поднимает локальный сервер на `http://localhost:11434`, который работает в фоне и принимает HTTP-запросы. Когда вы обращаетесь к нужному эндпоинту с вопросом — сервер прогоняет его через модель и возвращает ответ.

То есть с точки зрения Python-кода LLM — это просто веб-сервис. Никакой разницы с вызовом облачного API вроде GPT-4 или Claude, кроме адреса: вместо `api.openai.com` — `localhost`.

Ollama предоставляет несколько эндпоинтов. Самые важные:

- `POST /api/generate` — дать промпт, получить сгенерированный ответ;

Структура запроса к `/api/generate` минимальна: нужно указать модель, передать промпт и дождаться ответа. Тело запроса — JSON, ответ — тоже.
Минимальный пример:
```python
import requests

response = requests.post(
    "http://localhost:11434/api/generate",
    json={
        "model": "qwen2.5:1.5b",
        "prompt": "Привет! Назови одно интересное свойство Python в одном предложении.",
        "stream": False,
    },
    timeout=120,
)

data = response.json()
print(data["response"])
```
Что здесь происходит:
- model — имя модели в локальном хранилище Ollama. У нас это `qwen2.5:1.5b`.
- `prompt` — текст, который модель должна продолжить. Сюда мы будем класть будущий промпт с инструкцией и контекстом.
- `stream: False` — просим Ollama вернуть полный ответ одним JSON. Если поставить True, модель будет присылать ответ по токенам — удобно для интерактивных интерфейсов, но в Python-коде усложняет обработку.
- `timeout=120` — таймаут в 120 секунд. На CPU модель отвечает не мгновенно, и слишком короткий таймаут может прервать генерацию на середине.

В ответе нас интересует только поле `response` — там лежит сгенерированный текст. Остальные JSON-поля (статистика по токенам, время инференса, использованная модель) — служебные.

# Промпт с контекстом: главное в RAG

Сейчас `generate_answer()` отвечает из памяти модели. Спросите «как сменить папку с моделями в Ollama?» — Qwen попытается вспомнить и выдаст что-то правдоподобное, но не обязательно верное. Именно ради борьбы с этим мы и строим RAG-систему.

Чтобы модель отвечала по нашей документации, нужно правильно собрать промпт. Хороший RAG-промпт состоит из трёх частей:

1. **Системная инструкция** — кто такая модель, на какие данные опирается и как должна себя вести.
2. **Контекст** — найденные на этапе поиска чанки документации.
3. **Вопрос пользователя** — то, на что нужно ответить.
Всё это склеивается в одну строку и передаётся в `generate_answer()`. Вот рабочий шаблон:
```python
PROMPT_TEMPLATE = """Ты ассистент по документации Ollama.
Отвечай на вопрос пользователя, опираясь только на приведённые ниже фрагменты документации.
Если ответа во фрагментах нет - честно скажи, что не знаешь.
Ответ давай на русском языке.
В конце ответа на отдельной строке укажи источник в формате: Источник: <имя файла>.

Фрагменты документации:
{context}

Вопрос пользователя: {question}

Ответ:"""


def build_prompt(question: str, retrieved: list[dict]) -> str:
    """Собирает промпт из системной инструкции, контекста и вопроса."""
    context_parts = []
    for r in retrieved:
        context_parts.append(f"[файл: {r['source']}]\n{r['text']}")
    context = "\n\n---\n\n".join(context_parts)
    return PROMPT_TEMPLATE.format(context=context, question=question)
```
Разберём главные решения в этом шаблоне.

Первая строка системной инструкции задаёт роль («ассистент по документации Ollama») — это помогает модели не уходить в общие рассуждения и держать рамки задачи.

Фраза «опираясь только на приведённые ниже фрагменты» — самая важная. Без неё маленькая модель Qwen 2.5 1.5B легко начнёт смешивать данные из контекста со своими воспоминаниями из обучающего корпуса. С ней — заметно чаще держится приведённых фактов.

Просьба «если ответа нет, честно скажи» уменьшает количество выдумок: лучше получить «не знаю», чем правдоподобную ложь.

Перед каждым фрагментом мы пишем [файл: <имя>]и просим модель указывать источник в конце ответа. Пользователю сразу видно, откуда взята информация, а нам проще отлаживать систему: если ответ неверный, видно, какой именно чанк ввёл модель в заблуждение.
